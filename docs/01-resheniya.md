# Принятые решения (ADR)

Решения приняты заказчиком 14.08.2026 по итогам анализа `00-analiz-tz.md`.
Этот документ имеет приоритет над обоими исходными ТЗ при их расхождении.

## Р-1. Монетизации нет
Приложение бесплатно для пользователей и бесплатно в эксплуатации для владельца.
Из ТЗ-2 **исключаются**: PRO-аккаунты, платная B2B-витрина, White-Label, интеграция с 1С.
Соответственно, таблицы `organizations` / `subscriptions` не создаются. Многопользовательский
доступ к профилю (5 экспедиторов) реализуется, если понадобится, через таблицу `profile_members` —
схема к этому готова, так как сделки привязаны к профилю, а не к пользователю.

**Следствия для инфраструктуры (тариф 0 ₽):**

| Компонент | Сервис | Почему |
|---|---|---|
| Фронтенд (Mini App) | **Cloudflare Pages** | Бесплатный тариф разрешает коммерческое использование и не лимитирует трафик. Hobby-тариф Vercel формально ограничен некоммерческим применением, что для B2B-инструмента рискованно. |
| БД, API, Realtime | **Supabase Free** | Postgres + RLS + Realtime + Edge Functions в одном месте, без своего сервера. |
| Бот | **Supabase Edge Function** (вебхук) | Отдельный хостинг для бота не нужен. |
| Планировщик | **pg_cron** внутри Supabase | Просрочки, напоминания, авто-freeze. |
| Бэкапы | **GitHub Actions** → `pg_dump` в приватный репозиторий | На Free-тарифе Supabase нет PITR, поэтому свои бэкапы обязательны. |
| Медиа | **Telegram (file_id)** | Безлимитно и бесплатно, в отличие от 1 ГБ Supabase Storage. См. Р-8. |

**Границы бесплатного тарифа, которые принимаем осознанно:** ~500 МБ БД, ~200 одновременных
Realtime-соединений, засыпание проекта после недели полного простоя (лечится ежедневным cron),
отсутствие SLA. Требование NFR-016 (10 000 одновременных пользователей) на бесплатном тарифе
недостижимо и **заменяется** на: сотни одновременных, тысячи зарегистрированных. Переход на
Supabase Pro при росте не требует изменений в коде.

## Р-2. Рейтинг — приватная двусторонняя статистика
Принят вариант ТЗ-2. Публичные звёзды и текстовые отзывы (FR-062…FR-070) **отменяются**.
Вместо них: по каждой паре профилей видна история — сколько сделок закрыто, сколько в срок,
сколько просрочено, сколько аннулировано, общий оборот. Видна только двум сторонам этой пары.
Снимается внутреннее противоречие ТЗ-1 (FR-064 против NFR-001), а также отпадает потребность
в автомодерации оскорблений (FR-070).

## Р-3. Телефон не собираем
Принят вариант ТЗ-1 (FR-002, NFR-031). Номер телефона не запрашивается и не хранится ни в каком
виде, включая хеш. «Синяя галочка» из ТЗ-2 сохраняется как понятие, но выдаётся не за телефон,
а за поведение: аккаунт старше N дней **и** есть закрытые сделки с подтверждением обеих сторон.
Формулировка оферты «мы не храним персональные данные» остаётся корректной.

Остаточный риск: связка `telegram_id + имя + username + история сделок` при строгом прочтении
152-ФЗ всё равно может считаться персональными данными, а Supabase размещён вне РФ. Риск принят
осознанно ради нулевой стоимости; при масштабировании возможен перенос БД в российское облако
без изменения кода (Supabase self-hosted — тот же Postgres).

## Р-4. Частичная оплата — гибрид
- Все платежи фиксируются в отдельной таблице `payments`, остаток считается автоматически.
- Частичная оплата **без переноса срока** — просто платёж; сделка остаётся одна, помечается
  как частично оплаченная (модель ТЗ-1, FR-029).
- Частичная оплата **с переносом срока на остаток** — порождается дочерняя сделка с `parent_deal_id`,
  требующая нового акцепта даты (модель ТЗ-2, разд. III.3). Родительская закрывается на внесённую сумму.

## Р-5. Мультипрофильность — в схему сразу, в интерфейс позже
Таблица `profiles` и привязка сделок к `profile_id` делаются с первого дня. В MVP пользователю
автоматически создаётся один профиль, переключатель в UI скрыт. Экран переключения профилей и
выбор профиля при создании из чата (FR-011) — в v1.3.

## Р-6. «Просрочена» — признак, а не статус
Статус сделки сохраняет факт акцепта (`accepted`), а просрочка вычисляется как
`due_date < сегодня AND остаток > 0 AND status IN ('accepted','negotiation')`. В интерфейсе
красится оранжевым согласно FR-035. Причина: перевод в отдельный статус `overdue` уничтожал бы
информацию о том, была ли сделка подтверждена, и ломал бы переходы (что делать с просроченной
сделкой, по которой идут переговоры).

## Р-7. Тупик неподтверждённой оплаты
Проблема: FR-030 требует подтверждения оплаты обеими сторонами, а п. 8.2 ТЗ-1 признаёт, что от
злонамеренного молчания система не защищает. Решение:
1. Должник отмечает оплату → платёж в статусе `claimed`, обе стороны видят его в карточке.
2. **Начисление просрочки останавливается сразу** в момент заявления — иначе молчание кредитора
   бесплатно портит статистику должнику.
3. Кредитор получает уведомление и кнопку «Подтвердить» / «Отклонить».
4. Если кредитор молчит 7 дней (значение настраивается), платёж автоматически переходит в
   `confirmed` с пометкой «подтверждено автоматически» в истории. Кредитор предупреждается об
   этом в уведомлении и может отклонить платёж в любой момент до истечения срока.

## Р-8. Медиа — только `file_id` Telegram
Supabase Storage не используем: 1 ГБ на бесплатном тарифе кончится быстро, а файлы попадут под
режим ПДн. Вместо этого: файл отправляется боту (в личный чат или из Mini App), бот сохраняет
`file_id`, и по запросу любой стороны сделки пересылает файл этой стороне. Хранение в Telegram
бесплатно и без лимита объёма.

Отменяется как технически нереализуемое: FR-043 и FR-072 в части «бот сохраняет файлы, отправленные
в личном чате двух пользователей» — у бота нет доступа к чужой переписке. Ссылки на сообщения
(`chat_id` + `message_id`) не хранятся, так как второй стороне они всё равно не откроются.

## Р-9. Аннулирование сделки — только двустороннее
Закрывается дыра ТЗ-2 (разд. III.4): если бы кнопку «Аннулировать» в замороженной сделке мог
нажать один участник, должник обнулял бы долг, просто затянув спор до заморозки. Правила:
- **до акцепта** — инициатор может отозвать своё предложение, контрагент может отклонить (это
  штатный `cancelled`, односторонне);
- **после акцепта** — аннулирование только по согласию обеих сторон (как FR-032);
- в замороженной сделке односторонне доступны: «Принять предложенное» и «Предложить аннулировать».

## Р-10. Удаление аккаунта — анонимизация
FR-004 (полное удаление за 30 дней) корректируется: профиль обезличивается (имя → «Удалённый
профиль», `telegram_id` и username стираются), а сделки остаются у контрагента как доказательство
обязательства. Иначе один пользователь уничтожал бы данные другого, который об этом не просил.
Формулировка выносится в оферту.

## Р-11. Прочие фиксации
- **Часовой пояс** всей бизнес-логики — MSK (UTC+3). `pg_cron` работает в UTC, поэтому ежедневная
  задача «00:01 МСК» ставится на `01 21 * * *` UTC.
- **Суммы** — целое число копеек (`BIGINT`), валюта `RUB` фиксирована (FR-015), колонка `currency`
  оставлена на будущее.
- **Срок оплаты** — `DATE` без времени, а не `timestamptz`: «оплата 15 августа» не имеет времени суток.
- **Авторизация** — обмен Telegram `initData` на короткоживущий JWT в Edge Function; клиент ходит
  в Supabase с этим JWT, поэтому RLS и Realtime работают штатно. Все изменения данных — через
  `SECURITY DEFINER` RPC-функции в Postgres, чтобы машину состояний нельзя было обойти из клиента.
- **Контрагент в inline-режиме** определяется тем, кто нажал «Подтвердить». Telegram не сообщает
  боту адресата инлайн-сообщения, поэтому иначе никак. FR-022 (автоопределение контрагента в
  групповом чате по контексту) отменяется.
- **Фронтенд** — React + TypeScript + Vite + `@telegram-apps/sdk`.
- **Язык интерфейса** — русский.
