# Анализ двух ТЗ и предложение по объединённой модели

Дата: 14.08.2026
Документы на входе:
- **ТЗ-1** — «Мост долгов» (`TZ_Most_Dolgov_Telegram_MiniApp.md`): подробное продуктовое ТЗ, 102 FR + 38 NFR.
- **ТЗ-2** — «B2B/B2C Telegram-платформа»: короткое архитектурное ТЗ (стек, схема БД, ключевые механики, бизнес-модель).

---

## 1. Резюме

Это **не два описания одного продукта, а два разных продукта с общим ядром**.

| | ТЗ-1 «Мост долгов» | ТЗ-2 «B2B/B2C платформа» |
|---|---|---|
| Суть | Бесплатная утилита учёта долгов между поставщиком и магазином | B2B-SaaS с переговорным контуром и планом монетизации |
| Сильная сторона | Проработка продукта: сценарии, экраны, статусы, календарь, отчёты, право | Проработка техники: конкретный стек, схема БД, RLS, механика negotiation/split/freeze |
| Слабая сторона | Архитектура «в общем виде» (PostgreSQL/MongoDB, Redis, «сервисы»), нет механики торгов | Нет продуктовой глубины: нет календаря, отчётов, мультипрофиля, настроек уведомлений, правовой части |

**Вывод:** документы дополняют друг друга примерно на 70 %, но имеют **8 прямых противоречий**, которые нельзя реализовать одновременно. Их надо снять решением заказчика до старта разработки — часть из них меняет схему БД, а не только UI.

Базовая рекомендация: **берём продуктовый объём из ТЗ-1, техническую архитектуру и механики сделок из ТЗ-2.**

## 2. Прямые противоречия между ТЗ-1 и ТЗ-2

### 2.1. Монетизация — критично
- **ТЗ-1**, п. 1.5 и 8.1: «Проект полностью бесплатный для всех пользователей на всех этапах», «без платных подписок и рекламы».
- **ТЗ-2**, разд. V: Freemium — PRO-аккаунты для оптовых баз, платная B2B-витрина спонсорских карточек, White-Label.

Влияние: платная модель требует в схеме БД сущностей `organizations` (тенант), `memberships` (5 экспедиторов на профиль), `subscriptions`, а также разделения прав внутри организации. Заложить это позже «сверху» = переписать RLS и половину доступа к данным. Решать надо сейчас, реализовывать можно потом.

Отдельно: если продавать PRO **внутри Mini App**, правила Telegram требуют проводить оплату цифровых услуг через **Telegram Stars**; обычный эквайринг внутри TMA для цифровых товаров не допускается. Обход — оплата на внешнем сайте вне приложения.

### 2.2. Рейтинг: публичный или приватный — критично
- **ТЗ-1**, FR-062…FR-067: рейтинг 1–5 звёзд / 0–100 %, **публичные отзывы, видны всем пользователям**.
- **ТЗ-2**, разд. IV: «Полный отказ от публичного рейтинга. Пользователи видят историю только в рамках своих двусторонних отношений».

Дополнительно: **ТЗ-1 противоречит сам себе** — FR-064 (рейтинг виден всем) против FR-068 и NFR-001 (конкуренты не видят данные друг друга, изоляция).

Моя рекомендация — вариант ТЗ-2 (bilateral stats). Причины: публичный рейтинг в B2B-нише мгновенно превращается в инструмент давления и слива клиентской базы (по отзывам видно, кто с кем работает и на какие суммы), требует модерации (FR-070) и создаёт для вас юридический риск как для распространителя порочащих сведений. Приватная двусторонняя статистика даёт 90 % пользы без этих рисков.

### 2.3. Номер телефона и «синяя галочка» — критично, правовой риск
- **ТЗ-1**, FR-002 и NFR-031: телефон и любые ПДн **не запрашиваются и не хранятся**.
- **ТЗ-2**, разд. IV: верификация профиля по подтверждённому номеру телефона.

Технически подтвердить телефон легко (`KeyboardButton.request_contact` — номер приходит от Telegram, подделать нельзя). Проблема правовая, см. п. 4.

### 2.4. Частичная оплата: остаток в записи или сплит — влияет на схему БД
- **ТЗ-1**, FR-029: статус «Частично оплачена», остаток указан **в той же записи**.
- **ТЗ-2**, разд. III.3: сделка **программно делится на две** — историческая (`completed`) + новая на остаток с `parent_id`.

Рекомендация — гибрид: физически хранить платежи в отдельной таблице `payments`, а «сплит» ТЗ-2 использовать только когда **переносится срок** остатка (то есть нужен новый акцепт новой даты). Тогда: частичная оплата без изменения срока = просто платёж и остаток; частичная оплата с переносом срока = порождение дочерней сделки. Это закрывает оба ТЗ и не ломает историю.

### 2.5. Набор статусов — влияет на схему БД
- **ТЗ-1**: `Черновик → На согласовании → Активна → [Частично оплачена] → Оплачена`, плюс `Просрочена`, `Отменена`.
- **ТЗ-2**: `pending, accepted, negotiation, frozen, completed, cancelled`.

В ТЗ-2 нет «черновика», «частично оплачена» и «просрочена»; в ТЗ-1 нет `negotiation` и `frozen` — а это как раз самые ценные механики ТЗ-2. Нужен единый enum (предложение в п. 6.2).

Отдельно: **«Просрочена» не должна быть статусом**. Если перевести подтверждённую сделку из `active` в `overdue`, теряется факт акцепта и ломаются переходы (что делать с просроченной сделкой, по которой идут переговоры?). Правильно — вычисляемый признак `due_date < today AND status IN (active, negotiation)`; в UI он красится в оранжевый ровно как требует FR-035.

### 2.6. Переговоры об изменении условий
- **ТЗ-1**: механики нет вовсе. Есть только «Изменить» на этапе предпросмотра до создания.
- **ТЗ-2**, разд. III.2: полноценный контур — `proposed_changes` (JSONB), статус `negotiation`, экран «Было/Стало», кнопки «Принять / Обсудить в чате / Встречное предложение», запрет односторонних правок.

Противоречия нет, ТЗ-2 просто богаче. Берём целиком — это, на мой взгляд, главная ценность второго документа.

### 2.7. Мультипрофильность
- **ТЗ-1**, FR-006…FR-012: один Telegram-аккаунт → несколько профилей поставщика/магазина; **запись привязана к профилю, а не к аккаунту**.
- **ТЗ-2**: схема этого не поддерживает — `events.initiator_id → users.id`.

Схему ТЗ-2 придётся расширить таблицей `profiles`, а `events` привязать к `profile_id`. Это дешёвая правка **сейчас** и дорогая миграция **потом** (переписывание RLS + всех запросов). Даже если мультипрофиль отложить в v1.3 как в плане ТЗ-1, поле в схеме надо заложить сразу.

### 2.8. Стек и инфраструктура
- **ТЗ-1**, разд. 4: абстрактно — PostgreSQL **или** MongoDB, Redis для сессий/кэша, самописный REST API, 6 «сервисов».
- **ТЗ-2**, разд. I: конкретно — Supabase (Postgres + Realtime + Edge Functions), фронт на Vercel/Cloudflare Pages, free tier.

Рекомендация — стек ТЗ-2. Redis на старте не нужен (rate limiting и кэш закрываются Postgres + `pg_cron`); «6 сервисов» из ТЗ-1 — это логические модули, а не отдельные деплои.

## 3. Технические ограничения Telegram, под которые ТЗ придётся править

Это не противоречия между документами, а места, где ТЗ описывает поведение, **невозможное или ограниченное в Telegram API**. Каждое требует изменения сценария.

1. **Inline-режим не знает получателя.** FR-039/FR-041 и ТЗ-2 III.1 предполагают, что бот «отвечает в чат карточкой» и знает вторую сторону. В реальности при `@botname 5000 15 августа` бот получает `inline_query` только от **отправителя**; кто адресат — API не сообщает. Следствие: **контрагент определяется тем, кто нажал «Подтвердить»** на инлайн-карточке, и никак иначе. Это же закрывает FR-022 (в группе «определить контрагента по контексту» невозможно — только по клику).
   Дополнительно: чтобы бот вообще узнал о выборе результата, в @BotFather нужно включить `/setinlinefeedback`.

2. **Бот не может написать первым.** Уведомления (FR-055, FR-058) дойдут только до пользователя, который уже нажал `/start`. Для незарегистрированного контрагента доступна только инвайт-ссылка — что ТЗ-1 в FR-021 корректно и предусматривает.

3. **Бот не видит переписку в чужом личном чате.** FR-043 («в чат можно прикреплять фото — бот сохраняет их к записи») и FR-044/FR-072 («система хранит только ссылки на сообщения») в личном чате двух людей **нереализуемы**: у бота нет доступа к этим сообщениям, а `message_id` чужого чата второй стороне не откроется. Рабочие варианты: медиа загружаются (а) в Mini App, (б) отправкой боту в личку. Хранить: `file_id` (бот сможет переслать файл любой стороне) и/или копию в Supabase Storage. Замечу, что модель «файлы живут в Telegram» ещё и означает, что при удалении чата вложение теряется — ТЗ-1 это признаёт в п. 8.1, но для «цифровой расписки» (FR-024) это плохо: доказательство исчезает.

4. **`initData` Mini App подписывается и валидна ограниченное время.** Для Supabase Realtime с RLS клиенту нужен настоящий JWT — значит, нужен обмен `initData` → короткоживущий JWT в Edge Function (детали в п. 5.1).

5. **Deep-link payload ограничен**: `t.me/bot?start=PAYLOAD`, до 64 символов из `[A-Za-z0-9_-]`. Значит, в ссылку кладём только токен приглашения, а данные сделки — в таблицу `invites`.

6. **Telegram Stars** — см. п. 2.1, актуально только если монетизация внутри TMA.

## 4. Правовые риски (РФ)

ТЗ-1 хорошо проработан юридически (NFR-031…NFR-038), но два момента нужно обсудить.

1. **152-ФЗ и локализация данных.** ТЗ-1 утверждает, что ПДн не обрабатываются, потому что не собираются ФИО/ИНН/телефон. На практике связка `telegram_id + имя + username + аватар + история сделок` с высокой вероятностью квалифицируется как персональные данные. Из этого следует: нужно уведомление в Роскомнадзор об обработке ПДн, и **первичная запись ПДн граждан РФ должна выполняться в базе на территории РФ** (ч. 5 ст. 18 152-ФЗ). Supabase Cloud расположен вне РФ. Варианты:
   - (а) хостить Postgres в РФ (Yandex Cloud / Selectel / VK Cloud), Supabase — как self-hosted;
   - (б) остаться на Supabase Cloud и принять риск;
   - (в) остаться на Supabase Cloud, но зеркалировать первичную запись в РФ-базу.
   Это решение заказчика, но принимать его надо **до** выбора хостинга, а не после.
   Если добавляется телефон (п. 2.3), риск возрастает: телефон — однозначно ПДн, и «мы не храним ПДн» из оферты придётся убрать.

2. **Право на забвение против двусторонних записей.** FR-004 обещает полное удаление данных за 30 дней. Но сделка принадлежит двум сторонам: удалив её, вы уничтожаете доказательство долга у контрагента, который ничего не просил. Стандартное решение — **анонимизация** (профиль обезличивается, сделки остаются как «Удалённый профиль»), с явной фиксацией этого в оферте. Требует правки FR-004.

Ещё две несостыковки внутри ТЗ-1, не правовые, но важные:

3. **NFR-016 (10 000 одновременных пользователей) против free tier.** На бесплатных тарифах Supabase/Vercel это недостижимо: лимит одновременных Realtime-соединений и размер БД упрутся раньше. 10 000 **одновременных** — это порядка сотен тысяч зарегистрированных; нужен Supabase Pro и выше. Плюс NFR-017 (uptime 99.5 %) — на free tier SLA отсутствует в принципе.

4. **Тупик подтверждения оплаты.** FR-030/FR-033 требуют подтверждения оплаты обеими сторонами, а п. 8.2 признаёт, что от злонамеренного отказа система не защищает. Итог: должник заплатил, кредитор молчит — запись висит «просроченной» и портит статистику должнику. Нужен явный механизм: например, статус «оплата заявлена» виден обеим сторонам, счётчик просрочки останавливается, а через N дней молчания запись автоматически переходит в «оплачено по заявлению» с соответствующей пометкой в истории. Это надо решить продуктово.

## 5. Замечания к схеме БД из ТЗ-2

### 5.1. RLS и `auth.uid()` — так работать не будет
В ТЗ-2 указано условие `auth.uid() = initiator_id OR auth.uid() = partner_id`. Но `auth.uid()` — это идентификатор из `auth.users` Supabase, а вход у нас через Telegram `initData`, а не через Supabase Auth. Кроме того, при мультипрофиле сравнивать нужно не с пользователем, а с его профилями.

Рабочая схема:
1. Edge Function `auth` принимает `initData`, проверяет HMAC-подпись ботом, апсертит пользователя.
2. Возвращает JWT, подписанный секретом проекта, с claims `sub = users.id` и `profile_ids = [...]`.
3. Клиент отдаёт этот JWT в supabase-js → RLS и Realtime работают штатно.
4. Политика: `initiator_profile_id = ANY(current_profile_ids()) OR partner_profile_id = ANY(current_profile_ids())`.

Альтернатива — весь доступ через Edge Functions с `service_role`, но тогда теряется Realtime «из коробки», ради которого Supabase и выбирался.

### 5.2. Остальное по схеме
- `amount` — только **целое в копейках** (`BIGINT`), никаких `float`. Валюта ₽ фиксирована (FR-015), но колонку `currency` лучше оставить.
- `event_date` — это **срок платежа**, для него нужен `DATE`, а не `timestamptz`: «оплата 15 августа» не имеет времени, а `timestamptz` создаст ошибки на границе суток при разных часовых поясах.
- `users.telegram_id BIGINT UNIQUE` — верно.
- Нужны отсутствующие в ТЗ-2 таблицы: `profiles`, `payments`, `attachments`, `invites`, `audit_log` (NFR-003 обязателен), `notification_settings` (FR-056/FR-057), `outbox` для надёжной доставки уведомлений.
- `proposed_changes JSONB` — стоит дополнить полями `proposed_by`, `proposed_at`, `round_no`, иначе «пинг-понг» из ТЗ-2 III.4 невозможно ни ограничить, ни отобразить.
- Индексы: `(partner_profile_id, status, due_date)`, `(initiator_profile_id, status, due_date)`, `parent_id`, `telegram_id`.

### 5.3. Дыра в механике `frozen`
ТЗ-2 III.4: в замороженной сделке доступны кнопки «Аннулировать» или «Принять предложенное». Если «Аннулировать» может нажать **одна** сторона — должник в одностороннем порядке обнуляет свой долг, просто затянув спор до заморозки. Это ломает весь смысл продукта.

Аннулирование обязано быть **двусторонним** (как в ТЗ-1 FR-032 — «по соглашению сторон»). Односторонний выход возможен только до акцепта (отзыв своего предложения) либо как «пометить спорной» — с фиксацией разногласия, но без исчезновения долга.

### 5.4. CRON и часовой пояс
ТЗ-2 задаёт запуск в 00:01. `pg_cron` в Supabase работает в **UTC**; 00:01 по Москве = `01 21 * * *` UTC предыдущего дня. Нужно зафиксировать: вся бизнес-логика дат — в MSK (UTC+3), поскольку аудитория — РФ и республики.

## 6. Предложение по объединению

### 6.1. Что откуда берём
| Блок | Источник | Комментарий |
|---|---|---|
| Стек, Supabase, Realtime, Edge Functions | ТЗ-2 | + JWT-мост для авторизации |
| Механика negotiation / frozen / proposed_changes | ТЗ-2 | ключевая ценность второго ТЗ |
| Сплит по `parent_id` | ТЗ-2 | но только при переносе срока остатка |
| Статусы, календарь, отчёты, экспорт, поиск, уведомления | ТЗ-1 | продуктовое ядро |
| Мультипрофиль | ТЗ-1 | заложить в схему сразу, UI — позже |
| Приватная двусторонняя статистика вместо звёзд | ТЗ-2 | требует решения (п. 2.2) |
| Правовой блок, оферта, audit log, шариатские ограничения | ТЗ-1 | без изменений, кроме FR-004 |
| Freemium / PRO / White-Label | ТЗ-2 | требует решения (п. 2.1) |

### 6.2. Предлагаемый единый статусный автомат
```
draft ──► pending ──►ac­cepted ──► completed
             │           │  ▲
             │           ▼  │
             │      negotiation ──► frozen ──► completed | cancelled
             ▼           │              │
         cancelled ◄─────┴──────────────┘

Признаки (не статусы): is_overdue, has_partial_payment, payment_claimed
```
- `draft` — только в Mini App (FR-026).
- `pending` — ждём акцепта второй стороны (FR-027).
- `accepted` — обе стороны подтвердили, долг зафиксирован (FR-028 / ТЗ-2 `accepted`).
- `negotiation` — есть непринятое предложение об изменении (ТЗ-2 III.2).
- `frozen` — спор завис после срока, пинг-понг заблокирован (ТЗ-2 III.4).
- `completed` — оплачено и подтверждено (FR-030).
- `cancelled` — отклонено до акцепта либо аннулировано по согласию обеих сторон.

### 6.3. Предлагаемый объём MVP (4–6 недель)
1. Авторизация через `initData` + JWT-мост, оферта при первом входе.
2. Профили (с заделом под мультипрофиль), схема БД + RLS.
3. Создание сделки в Mini App и через inline (`@bot 5000 15 августа`) с парсером суммы/даты на русском.
4. Акцепт/отклонение второй стороной, deep-link приглашение для незарегистрированных.
5. Список сделок + карточка + история изменений (audit log).
6. Отметка и подтверждение оплаты, частичная оплата.
7. Календарь со сводкой на месяц.
8. `pg_cron`: просрочка, напоминания, авто-freeze зависших переговоров.
9. Уведомления через бота + настройки напоминаний.

Вне MVP: negotiation-контур (v1.1), отчёты PDF/Excel (v1.2), двусторонняя статистика (v1.2), мультипрофиль в UI (v1.3), PRO/витрина (v2.0).

## 7. Вопросы к заказчику
