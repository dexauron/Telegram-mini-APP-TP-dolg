# ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ-2)

**Проект:** B2B/B2C Telegram-платформа для фиксации договорённостей, учёта заявок и взаиморасчётов.

## I. АРХИТЕКТУРА И СТЕК ТЕХНОЛОГИЙ
- **Клиентская часть:** Telegram Mini App (TMA).
- **Среда бота:** Inline Mode (инлайн-режим) + Deep Linking (для онбординга через WhatsApp).
- **Фронтенд:** React/Vue, хостинг — Vercel или Cloudflare Pages (Free Tier).
- **Бэкенд и База данных:** Supabase (PostgreSQL).
- **Интеграция:** Supabase Realtime (синхронизация интерфейсов по WebSockets), Edge Functions (обработка вебхуков Telegram).

## II. СТРУКТУРА БАЗЫ ДАННЫХ (SUPABASE)

### 1. Таблица `users` (Профили)
- `id` (UUID, Primary Key)
- `telegram_id` (BigInt, Unique)
- `verified` (Boolean, подтверждение личности)

### 2. Таблица `events` (Сделки/Договорённости)
- `id` (UUID, Primary Key)
- `parent_id` (UUID, FK → events.id — для связи при частичной оплате)
- `initiator_id` (UUID, FK → users.id)
- `partner_id` (UUID, FK → users.id)
- `amount` (Integer/Decimal)
- `event_date` (Timestamptz)
- `proposed_changes` (JSONB — хранение временных данных при торгах)
- `status` (Enum: pending, accepted, negotiation, frozen, completed, cancelled)

### 3. Политика безопасности (Row Level Security)
Строгая изоляция данных. Конкуренты не видят друг друга.
Условие доступа (SELECT/UPDATE): `auth.uid() = initiator_id OR auth.uid() = partner_id`.

## III. ПОЛЬЗОВАТЕЛЬСКИЕ СЦЕНАРИИ И ЛОГИКА

### 1. Создание и Онбординг
- **Внутри Telegram:** Инициатор вводит `@botname [Сумма] [Дата]`. Бот генерирует инлайн-карточку. Вторая сторона нажимает [Подтвердить].
- **Внешний канал:** Создание карточки в TMA → генерация реферальной Deep-ссылки → отправка в WhatsApp → при клике партнёр попадает в бота с готовой карточкой на подтверждение.

### 2. Изменение условий (Переговоры)
- **Запрет односторонних правок:** После утверждения изменение исходных данных невозможно.
- **Механика:** Инициатор предлагает новую дату/сумму. Данные пишутся в `proposed_changes`. Статус меняется на `negotiation` (жёлтый маркер). Вторая сторона получает уведомление «Было/Стало» и варианты: [Принять], [Обсудить в чате], [Встречное предложение].

### 3. Частичное исполнение (Сплит)
При внесении частичной суммы сделка программно делится на две:
- **Сделка А** (историческая): закрывается на внесённую сумму (статус `completed`).
- **Сделка Б** (остаток): генерируется новая запись с привязкой по `parent_id`, требующая утверждения новой даты.

### 4. Обработка просрочек (CRON-автоматизация)
- В 00:01 ежедневно система сканирует `events`.
- Сделки со статусом `accepted` и прошедшей датой переводятся в просроченные (уведомление-напоминание).
- Сделки со статусом `negotiation` (зависшие споры) и прошедшей датой принудительно переводятся в `frozen` (заморожено). Пинг-понг предложениями блокируется, доступны только кнопки [Аннулировать] или [Принять предложенное].

## IV. РЕПУТАЦИОННАЯ СИСТЕМА И БЕЗОПАСНОСТЬ
- **Приватная статистика (Bilateral Stats):** Полный отказ от публичного рейтинга (звёзды/оценки). Пользователи видят историю успешных и сорванных сделок только в рамках своих двусторонних отношений.
- **Верификация:** Внедрение «Синей галочки» для профилей с подтверждённым номером телефона (защита от анонимного фрода).
- **Shadowban:** Серверная блокировка аккаунтов, рассылающих массовый спам инлайн-карточками.

## V. БИЗНЕС-МОДЕЛЬ (FREEMIUM B2B)
Базовый функционал для микробизнеса (фиксация долгов, заявок, календарь) — бесплатно.
Монетизация при масштабировании:
- **PRO-аккаунт для оптовых баз:** Многопользовательский доступ (один профиль для 5 экспедиторов), экспорт баз в Excel, интеграция с 1С (модель Иджара).
- **Нативная B2B-витрина:** Платное размещение спонсорских карточек производителей халяль-продукции в разделе «Предложения».
- **White-Label:** Продажа коробочного решения крупным региональным заводам под их собственный бренд.
